# Часть I. Флагман №1 - сервис приоритизации ручной проверки

## 1. Состав звеньев: что взято и что сознательно не взято

Постановка - табличный скоринг с ранжированием (ADR-001, версия v0.3). Отсюда состав:

**конвейер признаков --> модель --> калибровка --> порог и зона воздержания --> детерминированные правила ПОД/ФТ --> приоритизация --> валидация контракта --> очередь человека.**

| Звено | Взято? | Почему |
|---|---|---|
| Витрина признаков (point-in-time) | Да | Признаки должны быть такими, какими были на момент операции, иначе в обучение утекает будущее |
| Обучаемая модель оценки риска | Да, **одно звено** | Здесь и только здесь нужна закономерность, выучиваемая по примерам |
| Калибровка | Да | Порог увязывается с ценой обеих ошибок только если балл интерпретируем как вероятность |
| Наложение обязательных правил | Да | Противодействие отмыванию - обязанность: пороговый контроль перекрывает модель, а не наоборот |
| Человек в контуре | Да | Меры, затрагивающие права клиента, выносит сотрудник |
| Retrieval / база знаний | **Нет** | Нечего искать: ответ не извлекается из документов, а вычисляется по признакам операции |
| LLM, промпт, инструменты, агент | **Нет** | Нет задачи генерации; вынос данных за контур запрещён; для надзора нужно воспроизводимое объяснение, а не текст |
| Дообучение генеративной модели | **Нет** | Дорого, невоспроизводимо, не даёт ранжирования лучше табличной модели на этих признаках |

Свободный текст назначения платежа обрабатывается **внутри звена признаков** (локальные эмбеддинги, словарные и шаблонные признаки), а не отдельным языковым сервисом.

## 2. Таблица ответственности компонентов

| Компонент | Тип | Отвечает за | Не делает |
|---|---|---|---|
| Приёмник и нормализатор | код | Загрузка пакета операций, нормализация полей, парсинг текста назначения | Не оценивает риск, не отбрасывает операции |
| Построитель признаков | код | Агрегаты по клиенту и контрагенту, признаки дробления, транзитности, отклонения от профиля ОКВЭД | Не решает, что подозрительно |
| Проверка полноты признаков | детерминированный код | Триггеры fallback: пропуски, устаревание, значение вне обучающего диапазона, клиент без истории | Не чинит данные молча |
| **Модель оценки риска** | **обучаемое звено** | Сырой балл + вклад факторов | **Не выносит вердикт, не инициирует меру, не пишет в журнал напрямую** |
| Обёртка модели | код | Тайм-аут, версия весов, health-check, изоляция сбоя | Не подменяет ответ модели «правдоподобным» значением |
| Калибратор | код | Перевод балла в вероятность с поправкой на смещение отбора | Не меняет ранжирование по своему усмотрению |
| Порог и зона воздержания | детерминированный код | Применение порога, заданного комплаенсом; отметка зоны воздержания | Не подбирает порог автоматически под метрику |
| Наложение правил ПОД/ФТ | детерминированный код | Обязательный контроль перекрывает модель; сверка с сигналом правила | Не отменяет ни одного обязательного срабатывания |
| Приоритизатор | код | Порядок очереди: риск × сумма × возраст кейса | Не отбрасывает то, что не поместилось: остаток остаётся в очереди |
| Валидатор выходного контракта | детерминированный код | Проверка схемы, обязательных полей и ссылок на источник **до** постановки в очередь | Не пропускает неполный кейс «как есть» |
| Очередь кейсов | очередь | Хранение и упорядочивание, повторы, дедупликация | Не меняет содержимое кейса |
| Рабочее место аналитика | интерфейс | Карточка операции, факторы, ссылки на первичные данные, фиксация решения | Не показывает балл как вердикт |
| **Аналитик финмониторинга** | **человек** | Разбор, эскалация, приостановка, фиксация по процедуре | - |
| Журнал решений | хранилище (append-only) | Балл, версия модели, факторы, решение человека, причина | Не редактируется задним числом |
| Мониторинг | код | Вход, модель, очередь, бизнес-метрика; алерты и триггеры отката | Не принимает решение об откате самостоятельно (кроме guardrail-стопа) |
| Контрольная выборка | код + человек | Постоянная вероятностная выборка на экспертную разметку **независимо от очереди** | Не наполняется из того, что подняла модель |

## 3. Режим обработки

**Пакетный расчёт с внутридневным догоном.** Основной прогон - ночной, по закрытому операционному дню; догон - раз в час для операций текущего дня, попавших под пометку правил.

Почему не синхронный: сервис не стоит на пути платежа и не удерживает его - он упорядочивает работу службы. Синхронность создала бы зависимость проведения платежа от доступности ML-сервиса, чего быть не должно.

Последствия:
- **Задержка.** Приоритет по операции известен в пределах часа–суток. Для очереди, которая сегодня разбирается неделями, это не ограничение.
- **Повторы.** Прогон идемпотентен по ключу «операция + версия модели»: повторный расчёт не создаёт второй кейс, а обновляет балл, если кейс ещё не взят в работу.
- **Работа человека.** Аналитик утром получает готовую упорядоченную очередь; переупорядочивание уже взятых в работу кейсов запрещено, иначе разрушается ход разбора.
- **Отказ сервиса.** Молчание сервиса означает очередь в текущем порядке (по сумме) - деградация к сегодняшнему процессу, а не остановка работы.

## 4. Выходной контракт

```json
{
  "case_id": "b7f2…",                  // обязательное, идемпотентный ключ
  "operation_id": "OP-2026-09-04-…",   // обязательное, ссылка на первичный источник
  "client_id": "…",                     // обязательное
  "scored_at": "2026-09-05T02:14:00Z", // обязательное
  "model_version": "risk-rank@1.4.2",  // обязательное
  "feature_snapshot_id": "fs@2026-09-04", // обязательное, point-in-time срез
  "risk_score": 0.83,                   // обязательное, калиброванная вероятность
  "priority_rank": 27,                  // обязательное, место в очереди дня
  "decision_zone": "review | abstain | below_threshold", // обязательное
  "top_factors": [                      // обязательное, не пустое
    {"feature": "split_under_threshold_7d", "value": 6, "contribution": 0.21,
     "source_ref": "ops://acct/…/2026-08-28..2026-09-03"}
  ],
  "rule_signals": ["THRESHOLD_600K", "KYC_RISK_MEDIUM"], // обязательное (может быть пустым списком)
  "rule_model_agreement": "agree | model_only | rule_only", // обязательное
  "fallback_reason": null,              // null или код причины (см. §6)
  "data_completeness": 0.97             // обязательное
}
```

**Правила контракта:**
- **Обязательна ссылка на источник** у каждого фактора (`source_ref`): аналитик должен иметь возможность открыть первичные данные, а не верить баллу.
- **Детерминированные проверки до постановки в очередь:** схема валидна; `risk_score` в [0,1]; `top_factors` не пустые; `model_version` и `feature_snapshot_id` существуют в реестре; операция не имеет открытого кейса.
- **Поведение при отсутствии данных:** `risk_score` не выдаётся, кейс формируется с `decision_zone: "review"`, `fallback_reason` заполнен, приоритет назначается детерминированным правилом (сумма × сигнал правила). Пустое или отсутствующее значение никогда не подменяется нулём или средним.
- **Валидация до бизнес-действия:** ни одно поле контракта само по себе не приводит к действию в отношении клиента. Действие (приостановка, отказ, фиксация) возникает только после решения аналитика в интерфейсе, и в журнал пишутся обе части - что показала система и что решил человек.
- **Отдельно ведутся три следа** (`escalated`, `investigation_outcome`, `confirmed_case`) как разные поля кейса; склеивать их в одну метку запрещено на уровне схемы.

## 5. Уровень автоматизации

| Что | Уровень | Обоснование |
|---|---|---|
| Порядок очереди ручной проверки | **Модель делает сама** | Цена ошибки - только порядок разбора; ниже по списку операция не исчезает, а остаётся в очереди |
| Пометка операции обязательным правилом | Детерминированная автоматика | Обязанность банка, модель на неё не влияет |
| Вынесение операции на углублённое расследование | **Требует человека** | Юридические последствия и ответственность банка |
| Приостановка платежа, отказ в проведении, фиксация | **Только человек** | Затрагивает права клиента; автономное решение исключено |
| Исключение операции из очереди | **Запрещено автоматике** | Модель не может «закрыть» операцию: низкий балл означает лишь низкий приоритет |
| Изменение порога | Человек (комплаенс) | Порог - параметр процедуры внутреннего контроля, а не гиперпараметр модели |

## 6. Fallback: наблюдаемые признаки --> поведение

| Наблюдаемый признак | Код | Поведение системы | Куда уходит кейс |
|---|---|---|---|
| Признак отсутствует или устарел (нарушен срок актуальности витрины) | `FEATURES_STALE` | Балл не выдаётся | Детерминированный приоритет, флаг аналитику |
| Значение признака вне диапазона, виденного на обучении | `OUT_OF_RANGE` | Балл выдаётся, но помечен ненадёжным | Зона воздержания --> человеку |
| Клиент или сегмент без истории | `NO_HISTORY` | Модель не применяется | Детерминированный путь по правилам |
| Оценка в зоне воздержания около порога | `ABSTAIN` | Решение не принимается автоматикой | Человеку с пометкой «пограничный» |
| Расхождение модели и сигнала правила (`rule_only` / `model_only`) | `RULE_MISMATCH` | Приоритет по максимуму из двух | Человеку, расхождение логируется |
| Недоступна модель или сервис признаков | `MODEL_UNAVAILABLE` | Очередь строится текущим правилом (по сумме) | Процесс работает как сегодня |
| Отказ внешнего сигнала («Знай своего клиента») | `EXT_SIGNAL_DOWN` | Признак помечается пропущенным, не подставляется значение по умолчанию | Балл выдаётся с пометкой неполноты |
| Превышен лимит времени пакетного окна | `BUDGET_EXCEEDED` | Ранжируется успевшая часть, остальное - детерминированно | Очередь наполняется полностью в любом случае |

Общий принцип: **отказ любого звена деградирует систему до сегодняшнего процесса, а не останавливает работу службы.**

## 7. План мониторинга

| Слой | Что отслеживается | Порог/триггер | Действие |
|---|---|---|---|
| **Вход** | PSI/KL по ключевым признакам, доля пропусков, доля новых контрагентов, доля незнакомой лексики в назначении платежа - **в разбивке по сегменту** | PSI выше порога на срезе | Проверка сегмента, перекалибровка |
| **Вход** | Свежесть витрины признаков, полнота загрузки | Опоздание пакета | Автоматический fallback + алерт |
| **Модель** | Распределение балла, доля зоны воздержания, доля расхождений с правилом, латентность, доступность, версия весов | Сдвиг распределения; воздержание > 15 % | Расследование, при необходимости откат |
| **Очередь человека** | Глубина очереди, доля разобранного от помеченного, время до разбора, доля кейсов с fallback-причиной | Падение доли разобранного; рост глубины | Пересмотр порога/ёмкости |
| **Бизнес-метрика** | Доля результативных проверок в топе очереди, лаг обнаружения, число приостановок, число снятых приостановок, число жалоб | Ухудшение против контроля | Guardrail-стоп, откат к baseline |
| **Разметка** | Наполнение контрольной выборки, κ между экспертами | Выборка не пополняется; κ падает | Приёмка откладывается, дорабатывается гайдлайн |

**Что запускает повторную проверку или откат:** пробой любого guardrail (приостановки, жалобы, охват обязательного контроля), деградация Recall@k против baseline два периода подряд, дрейф входа выше порога на значимом сегменте, появление нового сегмента объёмом свыше 5 % потока. Порядок выкатки и отката - версия v0.9 сквозного ADR.

## 8. Угрозы на границах доверия

Границы отмечены на C4-схемах: B1 - внешний сигнал; B2 - клиентский свободный текст; B3 - веса и зависимости модели; B4 - выход модели --> бизнес-действие; B5 - периметр контура; B6 - сервисные доступы; B7 - интерфейс человека.

| Граница | Угроза | Контрмера |
|---|---|---|
| **B1** внешний сигнал «Знай своего клиента» --> признаки | Недоступность или изменение семантики сигнала молча меняет ранжирование; переоценка чужой оценки как собственной | Сигнал - один признак среди многих, не решающий; отсутствие фиксируется как пропуск, а не значение по умолчанию; окончательная оценка и ответственность остаются за банком |
| **B2** назначение платежа (текст пишет клиент) --> признаки | **Недоверенный контент.** Клиент подбирает формулировки под известные правила; текст может содержать конструкции, рассчитанные на обработчик текста | Текст используется только как источник числовых признаков, никогда как инструкция; генеративных звеньев в конвейере нет; экранирование при выводе в интерфейс; мониторинг незнакомой лексики |
| **B3** веса модели и зависимости | Подмена весов, неконтролируемое происхождение библиотек, «тихая» подмена версии | Реестр моделей с контрольными суммами и подписью; фиксация версий зависимостей; сборка из внутреннего зеркала; версия весов в каждом ответе и в журнале |
| **B4** выход модели --> бизнес-действие | Балл начинают трактовать как вердикт; ошибка модели превращается в меру против клиента | Валидатор контракта до очереди; в интерфейсе балл подписан как приоритет, а не как «схема»; меру выносит человек; журнал хранит обе части решения |
| **B5** периметр контура | Утечка сведений, составляющих банковскую тайну, и ПДн: выгрузки для обучения, логи с содержимым операций, отправка примеров вовне при отладке | Обучение и инференс внутри контура; внешние API отсечены архитектурно; логи без содержимого платежа (только идентификаторы и признаки); запрет выгрузки датасетов на рабочие станции; доступ по роли |
| **B6** сервисные доступы конвейера | Избыточные права сервиса (запись в АБС, доступ ко всем счетам) превращают ошибку в инцидент | Права только на чтение витрин и запись в очередь и журнал; отдельная учётная запись на звено; никаких прав на проведение или блокировку операций |
| **B7** интерфейс аналитика | Отравление обратной связи: массовые однотипные решения возвращаются как разметка; подмена решения в журнале | Журнал append-only; разметка из очереди не используется в одиночку (только вместе с контрольной выборкой); контроль аномалий в поведении разметчиков |

# Часть II. Инициатива №2 (+№18) - документный конвейер

**Режим обработки:** асинхронный по документу. Пакет ставится в очередь при загрузке, андеррайтер получает уведомление о готовности карточки. Синхронность не нужна: разбор пакета всё равно занимает часы; асинхронность позволяет повторять обработку тяжёлых сканов и не держать сессию.

**Выходной контракт:** JSON на **поле**, а не на документ: `field_name`, `value`, `unit`, `period`, `confidence`, `source_ref` (документ + страница + bbox), `extraction_method` (модель или шаблон). Обязательные детерминированные проверки до попадания в карточку: соответствие типу (дата - дата, сумма - число), арифметическая согласованность (итог равен сумме строк), кросс-документная сверка (обороты в выписке против отчётности), сверка реквизитов с внешними реестрами. **Поле без `source_ref` в карточку не попадает.** При отсутствии данных поле остаётся пустым и помечается «не извлечено» - пустое значение никогда не заменяется нулём.

**Уровень автоматизации:** поле с уверенностью выше порога и прошедшее детерминированные проверки подставляется автоматически (с подсветкой источника); ниже порога или при противоречии - человеку; кредитное решение всегда за андеррайтером.

**Fallback:** не прошла схема ответа; нет подтверждающего источника (bbox не найден); документы противоречат друг другу; тип документа не распознан или вне области применимости; качество изображения ниже порога (фото с бликом, обрез); отказ сервиса или превышение лимита - во всех случаях документ или конкретное поле уходит на ручной ввод, конвейер не гадает.

**Мониторинг:** доля автопринятых полей, доля исправленных андеррайтером (главный прокси-показатель качества), распределение уверенности, дрейф форматов и появление незнакомых шаблонов, глубина очереди верификации, фактическое время разбора пакета против baseline.

**Угрозы на границах доверия:** здесь **вход недоверенный по определению** - файл присылает клиент. B1 приём: вредоносный файл, «бомба» распаковки, встроенный активный контент --> карантин, антивирус, ограничение размера и времени, снятие скриптов, рендер в безопасный формат. B2 содержимое документа --> недоверенный текст никогда не трактуется как инструкция обработчику; извлечение работает по фиксированной схеме полей, свободных инструкций из документа система не исполняет. B3 подделка документа --> это отдельная инициатива №10, и конвейер её не подменяет: он извлекает то, что написано, и помечает арифметические несоответствия. B4 выход --> поле не влияет на решение без верификации человеком на низкой уверенности. B5 контур --> обработка и хранение внутри периметра, публичные OCR-API отсечены, доступ к оригиналам по роли. B6 доступы --> сервис имеет право писать только в своё хранилище и очередь, не в кредитный конвейер.

# Часть III. Инициатива №4 - прогноз просрочки по портфелю

**Режим обработки:** пакетный расчёт раз в месяц (и по требованию перед риск-комитетом). Онлайн не нужен: потребитель - регулярный управленческий цикл.

**Выходной контракт:** портфельный и сегментный прогноз: `segment`, `horizon`, `expected_overdue_rate`, `interval_low`, `interval_high`, `model_version`, `data_version`, `assumptions_ref`, `coverage_backtest`. Обязательны интервал и ссылка на допущения - точечное число без интервала в отчёт не выдаётся. **Оценка по отдельной сделке из контракта исключена архитектурно**: она остаётся внутренним артефактом расчёта и не экспортируется в кредитный конвейер (ограничение из ADR-004).

**Уровень автоматизации:** расчёт полностью автоматический, **решение - нет**: резервы и лимиты утверждает риск-комитет, прогноз идёт как вход в обсуждение вместе с бэктестом и допущениями.

**Fallback:** пропущены макропеременные на дату расчёта; сегмент с числом наблюдений ниже минимального; факт вышел за интервал прошлого прогноза; признаки вне диапазона обучения - в этих случаях по сегменту выдаётся не модельный прогноз, а экстраполяция винтажей с явной пометкой метода в отчёте.

**Мониторинг:** ежеквартальный бэктест на закрывшихся когортах, покрытие интервала, PSI по сегментам, стабильность состава портфеля, доля сегментов, ушедших на fallback.

**Угрозы на границах доверия:** B1 внешние макроданные --> подмена или пересмотр ряда задним числом искажает прогноз: фиксируется версия ряда на дату расчёта. B2 отчётность заёмщика --> потенциально искажённый вход (инициатива №10): ограничение признаётся в отчёте, признаки из отчётности не единственные. B3 воспроизводимость --> прогноз влияет на резервы, поэтому версия модели, версия данных и допущения хранятся вместе с числом. B4 выход --> главная угроза этой инициативы: использование сегментной или сделочной оценки как основания для отказа конкретному заёмщику. Контрмера архитектурная - оценка по сделке не покидает расчётный контур, экспорт только агрегатов. B5 контур --> расчёт внутри банка, ПДн заёмщиков-ИП не выгружаются во внешние сервисы.
