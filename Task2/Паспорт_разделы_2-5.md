# Раздел 2. Постановка

## №1 - приоритизация операций для финмониторинга (флагман)

| Поле | Что фиксируем |
|---|---|
| **Бизнес-действие** | Аналитик финмониторинга берёт из очереди следующую операцию для разбора. Меняется порядок этой очереди в пределах суточной ёмкости службы. |
| **Объект и единица решения** | Одна операция по счёту. Решение принимается по операции; часть признаков строится на уровне клиента и пары «клиент - контрагент». |
| **Момент** | Пачкой: ночной прогон по закрытому операционному дню и почасовой догон для операций текущего дня, попавших под пометку правил. Реальное время не нужно - сервис не стоит на пути платежа. |
| **Операция** | Порядок (ранжирование) с элементами поиска аномалий. **Не** категория: вердикт «схема / не схема» сознательно не выносится. |
| **Модальность** | Таблица + время (поведенческие агрегаты по окнам) + граф (цепочки контрагентов) + текст (назначение платежа, свободная форма). |
| **Выход модели** | Калиброванный балл риска в [0..1], топ-факторы вклада со ссылкой на источник, флаг зоны воздержания, версия модели и срез признаков. |
| **Бизнес-выход** | Упорядоченная очередь на сегодня: ~330 операций, отсортированных по ожидаемой полезности проверки, с карточкой контекста. Отличается от выхода модели: балл - не приоритет, приоритет считается детерминированно из балла, суммы и возраста кейса. |
| **Источник правильного ответа** | Готового эталона нет. Три следа ведутся раздельно: «эскалировано на расследование» (~400/мес, известен сразу, это мнение аналитика), «исход расследования» (недели, смещён), «формально подтверждённый случай» (единицы, месяцы). Рабочий источник для приёмки - вероятностная контрольная выборка, размеченная экспертами по гайдлайну с оценкой согласованности (κ). |
| **Конвейер** | Обучаемое звено одно - оценка риска операции. Детерминированы: нормализация, построение признаков, калибровка, порог и зона воздержания, наложение обязательных правил, приоритизация, валидация выходного контракта. Меру выносит человек. |
| **Альтернативные постановки** | (1) Классификация «схема / не схема» - отклонена: нет эталона и мешает ограничение об автоматизированных решениях. (2) Снижение ложных приостановок вместо выявления - держим в резерве: если контрольная выборка покажет ничтожную долю схем в непроверяемой части, приоритет смещается сюда. (3) Скоринг клиента вместо операции - отклонён: меры применяются к операции, а профиль клиента входит признаком. Различающий вопрос бизнесу - в строке уточнения раздела 1. |

## №2 (+№18) - документный конвейер кредитной заявки

| Поле | Что фиксируем |
|---|---|
| **Бизнес-действие** | Андеррайтер заполняет карточку кредитной заявки по пакету документов. Заполнение заменяется верификацией предзаполненного. |
| **Объект и единица решения** | Одно поле документа (значение показателя), а не документ целиком: решение об автоприёме принимается по полю. Второй уровень - документ (его тип и пригодность к обработке). |
| **Момент** | Асинхронно по загрузке пакета: андеррайтер получает карточку готовой. Синхронность не нужна - разбор всё равно занимает часы. |
| **Операция** | Извлечение (плюс категория на входе - классификация типа документа). |
| **Модальность** | Документ и изображение (PDF-сканы, фото с телефона), таблица (Excel, выгрузки бухсистем), текст. |
| **Выход модели** | Нормализованный JSON по каждому полю: значение, единицы, период, координаты источника (страница + область), уверенность, способ извлечения (модель или шаблон). |
| **Бизнес-выход** | Предзаполненная карточка заявки: поля выше порога уверенности подставлены с подсветкой источника, ниже порога и противоречия - в очереди верификации рядом с оригиналом. |
| **Источник правильного ответа** | Ручная транскрипция выборки исторических пакетов (известен сразу, стоит денег) и авторазметка: машиночитаемая выгрузка клиента - эталон для скана того же отчёта. |
| **Конвейер** | Обучаемые звенья: классификация типа документа, распознавание, извлечение полей из разнородных форм. Детерминированы: карантин и проверка файла, шаблоны для фиксированных форм, проверка типов, арифметическая и кросс-документная сверка, сверка с реестрами, порог уверенности, маршрутизация на верификацию. |
| **Альтернативные постановки** | (1) Полностью ручной ввод с улучшенным интерфейсом - baseline, с ним и сравниваем. (2) Давление на канал подачи (требовать машиночитаемые выгрузки) - дешевле, если их доля высока; различающий вопрос задан в разделе 1. (3) Извлечение сразу «решения по заявке» из документов - отклонено: это кредитное решение, оно остаётся за человеком. |

## №4 - прогноз годового уровня просрочки по портфелю МСБ

| Поле | Что фиксируем |
|---|---|
| **Бизнес-действие** | Риск-комитет утверждает размер резервов, лимиты и цену по сегментам портфеля МСБ. |
| **Объект и единица решения** | Решение принимается по сегменту и портфелю. Оценка по отдельной сделке - внутренний артефакт расчёта, наружу кредитного конвейера не отдаётся. |
| **Момент** | Пачкой, раз в месяц и по запросу перед риск-комитетом. Онлайн не нужен. |
| **Операция** | Прогноз (число) на горизонте 12 месяцев; на уровне сделки - вероятность события. |
| **Модальность** | Таблица + время (когорты, винтажи, макроряды). |
| **Выход модели** | Вероятность выхода в просрочку по сделке; после агрегации - ожидаемый уровень просрочки по сегменту и портфелю с интервалом. |
| **Бизнес-выход** | Отчёт риск-комитету: прогноз по сегментам с интервалом, результатами бэктеста, стресс-сценариями и списком допущений. Отличается от выхода модели: точечное число без интервала и допущений в отчёт не выдаётся. |
| **Источник правильного ответа** | Реализованный факт просрочки и дефолта по когорте. Возникает естественно, разметка не нужна, становится известен через 12 месяцев - отсюда обучение на закрытых когортах и разделение выборки по времени. |
| **Конвейер** | Обучаемое звено - оценка вероятности по признакам. Детерминированы: сборка когорт и признаков, калибровка, агрегация в портфель, интервалы, стресс-сценарии и экспертные надбавки, границы правдоподобия. |
| **Альтернативные постановки** | (1) Экстраполяция винтажей (текущий процесс) - baseline. (2) PD по каждому заёмщику как основание для решения по заявке - **отклонено**: попадает под ограничение из №12; различающий вопрос задан бизнесу в разделе 1. (3) Модель выживания (срок до события вместо факта) - остаётся кандидатом в шортлисте, если важен момент наступления. |

# Раздел 3. Оценка качества

## №1 - приоритизация операций (флагман)

| Поле | Что фиксируем |
|---|---|
| **Бизнес-метрика** | Число результативных проверок в месяц при неизменной ёмкости службы (результативная = закончилась эскалацией или отказом в проведении) и число лишних приостановок честных клиентов (сегодня 600 приостановок, 450 снятий, 120 жалоб в месяц). |
| **Положительный класс** | Операция, разбор которой окажется результативным, - то есть та, по которой аналитик примет меру или эскалирует. **Не** «операция является схемой»: такой метки не существует, и подменять одно другим нельзя. |
| **Метрика под решение** | Precision@k и Recall@k при k = суточной ёмкости (~330 операций/день). Отвечают на вопрос «достаточно ли»: решение принимается о том, что попадёт в те же 330 разборов, а не о каждой операции по отдельности. Дополнительно - калибровка (reliability curve): без неё порог нельзя увязать с ценой ошибки. |
| **Baseline** | Текущая сортировка очереди по сумме операции - то, как служба работает сегодня. Сравнение по тем же Precision@k / Recall@k на той же контрольной выборке. |
| **Проверочная выборка** | Вероятностная контрольная выборка, стратифицированная по суммам, сегментам, ОКВЭД и каналам, размеченная экспертами. Оценка честная именно потому, что выборка не зависит ни от правил, ни от модели: на очереди мерить нельзя - там смещение отбора. |
| **Рабочая точка** | Отбираемая верхушка = дневная ёмкость службы (~330). Порог отсечения задаёт комплаенс; вокруг него - зона воздержания ≤ 15 %, кейсы из неё уходят человеку с пометкой «пограничный». |
| **Показатели в этой точке** | Численные значения на момент проектирования не подставляются: нет ни доступа к кандидатам, ни размеченного набора, а цифры «из литературы» здесь были бы выдумкой. Фиксируем, что измеряем: доля результативных в топ-330 против baseline, доля подтверждений среди операций, которые правила не метили, а модель подняла, нагрузка на аналитика (кейсов в день не растёт). Приёмка - обгон baseline по Recall@k при неухудшении guardrails. |
| **Цена ошибок** | Пропуск: невыявленная схема -> риск предписания надзора (2 за прошлый год, устранение месяцами, оценочно ~6 млн ₽ каждое). Ложное срабатывание: приоритет отдан честной операции -> потраченные 12 минут аналитика (375 ₽) и, если дело дошло до приостановки, остановленный платёж, жалоба (оценочно 8 000 ₽) и риск ухода клиента. |
| **Guardrails** | Не должны ухудшиться: число приостановок и доля снятых, число жалоб, полнота охвата обязательного контроля, глубина очереди и время до разбора, доля кейсов на fallback, качество на каждом сегментном срезе (а не в среднем). |

## №2 (+№18) - документный конвейер

| Поле | Что фиксируем |
|---|---|
| **Бизнес-метрика** | Время разбора пакета андеррайтером (сегодня 1,5 часа) и доля полей, которые он не набирает вручную. |
| **Положительный класс** | Поле, извлечённое верно и пригодное к автоприёму (значение, единицы, период совпадают с эталоном). |
| **Метрика под решение** | Field-level accuracy по ключевым полям (суммы, даты, ИНН, период) и доля автоматически принятых полей при заданной точности автоприёма. CER/WER - диагностика, не приёмка: 2 % ошибок символов в номере счёта и в примечании стоят по-разному. |
| **Baseline** | Полностью ручной ввод: 1,5 часа на пакет и текущая частота опечаток андеррайтера, замеренная на том же наборе. |
| **Проверочная выборка** | 300–500 документов на каждый канал (скан / фото / машиночитаемая выгрузка) и ключевой тип, размеченные вручную, со стратификацией по бухгалтерским системам. Честность обеспечивается тем, что в набор целенаправленно добраны редкие формы, а не только «удобные» пакеты из архива. |
| **Рабочая точка** | Порог уверенности автоприёма поля. Всё ниже порога и все противоречия - на верификацию человеку. |
| **Показатели в этой точке** | Измеряем: долю ошибочно автопринятых полей (должна быть не выше частоты опечаток ручного ввода), долю автоприёма, фактическое время разбора пакета. Числовые пороги фиксируются после замера baseline на пилоте. |
| **Цена ошибок** | Ложный автоприём: неверная цифра уходит в кредитное решение - дороже всего, поэтому порог смещён в сторону осторожности. Пропуск (поле не извлечено): стоит ровно как сегодняшний ручной ввод, то есть ноль дополнительного ущерба. |
| **Guardrails** | Время разбора не выросло ни на одном типе пакета; очередь верификации не растёт неограниченно; доля документов, целиком ушедших на ручной ввод, не превышает согласованной; андеррайтер не теряет доступ к оригиналу рядом с полем. |

## №4 - прогноз просрочки по портфелю

| Поле | Что фиксируем |
|---|---|
| **Бизнес-метрика** | Точность планирования резервов: расхождение факта и прогноза уровня просрочки по портфелю за год, в процентных пунктах и в рублях резерва. |
| **Положительный класс** | Кредитная сделка, вышедшая в просрочку (событие фиксируется по согласованному определению: 90+ дней как основное, 30+ как мягкое при дефиците событий) в течение 12 месяцев от даты наблюдения. |
| **Метрика под решение** | На портфеле - абсолютная ошибка прогноза и покрытие интервала (доля периодов, где факт попал в заявленный интервал). На сделке - калибровка (Brier, reliability curve) и во вторую очередь ранжирование (Gini). Для резервов калибровка важнее ранжирования: хорошо ранжирующий, но смещённый прогноз даёт неверный размер резерва. |
| **Baseline** | Действующая экспертная экстраполяция винтажей. |
| **Проверочная выборка** | Закрывшиеся когорты с разделением **по времени**, а не случайным: обучение на ранних, проверка на поздних. Случайное разделение дало бы утечку будущего и завышенную оценку. Плюс сегментные срезы по ОКВЭД, региону, размеру. |
| **Рабочая точка** | Порога отсечения нет - выход не бинарный. Рабочая точка задаётся уровнем интервала (доверительная ширина), используемого риск-комитетом для резервирования. |
| **Показатели в этой точке** | Измеряем на бэктесте: ошибку прогноза по портфелю, покрытие интервала против номинального, устойчивость по сегментам. Числа появляются после первого прогона на закрытых когортах. |
| **Цена ошибок** | Занижение: недорезервирование, удар по капиталу при реализации риска и вопросы надзора. Завышение: замороженный капитал и отказ расти в нормальных сегментах. Ошибки несимметричны по последствиям, поэтому в отчёт идёт интервал, а не точка. |
| **Guardrails** | Прогноз не занижает на кризисных когортах; доля сегментов, ушедших на fallback (экстраполяцию), не растёт; состав портфеля в расчёте соответствует фактическому; оценка по отдельной сделке не покидает расчётный контур. |

# Раздел 4. Готовность данных

## №1 - приоритизация операций (флагман)

| Поле | Что фиксируем |
|---|---|
| **Решение** | Какое место операция займёт в сегодняшней очереди ручной проверки. |
| **Объект и гранулярность** | Запись - одна операция по счёту (20–25 млн в месяц). Признаки строятся на трёх уровнях: операция, клиент за окна времени, пара «клиент - контрагент» и цепочка контрагентов. |
| **Источник и владелец** | История операций и справочники - DWH/АБС, владелец ИТ. Отметки об эскалации и исходы - финмониторинг (владелец процесса). Правила внутреннего контроля и пороги - комплаенс. Сигнал уровня риска клиента - внешняя платформа «Знай своего клиента» (вспомогательный, ответственность за оценку остаётся на банке). |
| **Источник правильного ответа** | **Отсутствует как эталон.** Три следа разной надёжности: «эскалировано» (~400/мес, доступно сразу), «исход расследования» (недели), «формально подтверждено» (единицы, месяцы). Рабочий источник создаётся программой контрольной выборки. |
| **Доступность признаков в проде** | Признаки должны быть восстановимы на момент операции: витрина point-in-time, иначе в обучение утекает будущее (например, итоговый оборот месяца или более поздняя отметка риска). Признаки, известные только постфактум (исход расследования), в модель не подаются - только в оценку. |
| **Разметка** | Нет. Программа: гайдлайн финмониторинга, разметка контрольной выборки экспертами, оценка согласованности (κ Коэна/Флейса) на пересекающихся подвыборках. Разметка накапливается из двух источников одновременно - разобранная приоритетная очередь и контрольная выборка; только очередь брать нельзя. |
| **Смещение отбора** | **Критично.** Метки получили только те операции, которые отобрали пороговые правила и внешние сигналы; непроверенная операция не равна чистой. Про остальные 25 тыс. в месяц не известно ничего - это и закрывает вероятностная контрольная выборка. |
| **Репрезентативность** | Покрыты действующие сегменты клиентов банка; редкие но дорогие случаи (крупные схемы) представлены единицами. Новые сегменты не покрыты - см. случай селлеров маркетплейсов в разделе 5. Требуются сегментные срезы в приёмке и мониторинге. |
| **Объём** | Общий - избыточен (20–25 млн операций в месяц, история за годы). По важному классу - дефицит: ~4 800 эскалаций в год как прокси и единицы подтверждённых случаев. |
| **Качество** | Структурные поля полны; назначение платежа - свободный текст, качество разное; контрагенты дублируются и переименовываются (нужна нормализация); ОКВЭД устаревает; форматы каналов различаются. |
| **Право использовать** | Сведения об операциях и счетах - банковская тайна; клиенты, представители и поручители - субъекты ПДн. Ограничения на передачу и хранение определяются целью, основанием, договором с обработчиком и регионом. За ответом - к комплаенсу, DPO и юристам (список вопросов в [ADR-001](ADR-001_flagman_сквозной.md)). |
| **Вердикт** | **Разрыв с планом закрытия.** Для постановки «вердикт схема / не схема» - фактически заблокировано (нет эталона, плюс правовое ограничение). Для принятой постановки «ранжирование очереди» - можно начинать пилот при условии, что программа контрольной выборки стартует одновременно с сервисом. |

## №2 (+№18) - документный конвейер

| Поле | Что фиксируем |
|---|---|
| **Решение** | Какие значения полей подставить в карточку заявки автоматически, а какие отправить на верификацию человеку. |
| **Объект и гранулярность** | Запись - поле документа; над ним документ (тип, канал, качество) и пакет заявки. |
| **Источник и владелец** | Пакеты документов кредитных заявок, архив и текущий поток; владелец процесса - андеррайтинг, владелец хранилища - ИТ. Внешние реестры - для сверки реквизитов. |
| **Источник правильного ответа** | Ручная транскрипция выборки (доступна сразу, стоит денег) и авторазметка из машиночитаемых дублей. Эталон достижим - дефицит только в объёме. |
| **Доступность признаков в проде** | На вход подаётся тот же документ, что и в обучении, - расхождения «обучение / прод» минимальны. Риск в другом: новые версии бухгалтерских форм и новые каналы подачи появляются без предупреждения, поэтому тип документа определяется на входе, а незнакомый формат уходит на ручной ввод. |
| **Разметка** | Нужна, но выполняется операционистами по инструкции, без экспертной программы: 300–500 документов на канал и ключевой тип. Правки андеррайтера в интерфейсе возвращаются как разметка на дообучение. |
| **Смещение отбора** | Слабое: в архиве переоценены «удобные» форматы клиентов, которые уже прислали читаемые сканы. Закрывается целевым добором фото-канала и нестандартных форм в приёмочный набор. |
| **Репрезентативность** | Проверяется по каналам подачи, типам документов и версиям бухгалтерских систем; появление нового канала - триггер пересмотра. |
| **Объём** | Достаточен по массовым типам; по важному классу (редкие и «самопальные» формы) требуется целевой добор - именно на них происходят дорогие ошибки. |
| **Качество** | Разнородное: низкое разрешение сканов, блики и перекос на фото, нестандартные формы. Оригиналы сохраняются целиком, поэтому производные всегда восстановимы. |
| **Право использовать** | В документах - ПДн и сведения, составляющие банковскую тайну: обработка и хранение внутри контура, публичные OCR-API отсечены. К DPO - сроки хранения производных и разграничение доступа. |
| **Вердикт** | **Можно начинать пилот.** Самая готовая из трёх инициатив. |

## №4 - прогноз просрочки по портфелю

| Поле | Что фиксируем |
|---|---|
| **Решение** | Размер резервов, лимиты и ценообразование по сегментам портфеля МСБ на год. |
| **Объект и гранулярность** | Запись - кредитная сделка на дату наблюдения; решение принимается по сегменту и портфелю (агрегация из сделок). |
| **Источник и владелец** | Витрина кредитного портфеля и платёжной дисциплины (ИТ/DWH), отчётность заёмщиков (андеррайтинг), макроряды (внешний источник). Владелец модели и приёмки - риск-менеджмент. |
| **Источник правильного ответа** | Реализованный факт просрочки/дефолта по когорте. Возникает естественно, разметка не нужна; становится известен через 12 месяцев. |
| **Доступность признаков в проде** | Все признаки должны быть известны на дату наблюдения: отчётность - последняя сданная на эту дату (а не более поздняя), макропеременные - в редакции на дату, а не пересмотренные постфактум. Это главный источник скрытой утечки будущего в такой модели. |
| **Разметка** | Не требуется. |
| **Смещение отбора** | Обучение идёт на одобренных заявках - выжившая выборка. Модель применима к одобряемому потоку; для расширения нужен reject inference, и это оговаривается в отчёте риск-комитету, а не замалчивается. |
| **Репрезентативность** | По времени (когорты разных лет и режимов), ОКВЭД, региону, размеру. Не покрыты: новые сегменты и режимы, которых в истории не было. |
| **Объём** | **Ключевая неизвестная кейса** - число дефолтов. Общий объём портфеля достаточен; по важному классу требуется не менее нескольких сотен событий, иначе добавляется мягкая метка (30+/90+) и расширяется горизонт наблюдения. |
| **Качество** | Кредитная история и платёжная дисциплина надёжны. Отчётность заёмщиков может быть искажена (см. инициативу №10) - признаётся ограничением, а не игнорируется; макроряды пересматриваются задним числом, поэтому версия ряда фиксируется на дату расчёта. |
| **Право использовать** | ПДн заёмщиков-ИП и банковская тайна - обработка внутри контура. Правовой профиль мягче: выход - агрегат, не решение по субъекту. |
| **Вердикт** | **Можно начинать пилот** при подтверждении объёма положительного класса. Если событий меньше нескольких сотен - вердикт понижается до «разрыв с планом закрытия» с планом: мягкая метка плюс расширение горизонта. |

# Раздел 5. Карточка эксперимента

Карточка заполняется на главную неопределённость, от которой зависит решение. По флагману она заполнена дважды: **до запуска** (проектная неопределённость) и **после запуска** - по инциденту с новым сегментом, см. [Task5](../Task5/Деградация_модели_на_новом_сегменте.md).

## №1 - до запуска: добавляет ли модель что-то сверх правил

| Поле | Что фиксируем |
|---|---|
| **Где именно теряем** | В звене приоритизации, на классе «дробление под пороги» и на непроверяемой части потока (25 тыс. операций в месяц, которые служба не разбирает и о которых ничего не известно). |
| **Гипотеза причины** | Обучающий сигнал - производная от существующих правил (эскалация ставится по операциям, отобранным правилами), поэтому модель воспроизводит правила и не добавляет к ним ничего. |
| **Конкурирующие объяснения** | (1) Закономерности сверх правил в данных нет вовсе. (2) Закономерность есть, но не построены нужные признаки - графовые по цепочкам контрагентов и текстовые по назначению платежа. (3) Закономерность есть, но метки слишком шумные - эксперты не согласны между собой, и метрика меряет шум. (4) Закономерность есть, но приёмочная выборка нерепрезентативна: собрана из очереди, а не вероятностно. |
| **Рычаг** | Данные (контрольная выборка вместо очереди), признаки (граф + текст), метки (гайдлайн и κ), порог и постобработка. Функция ошибки - во вторую очередь. |
| **Дешёвый различающий эксперимент** | На одной и той же контрольной выборке сравнить четыре варианта: baseline «сумма»; модель только на признаках, производных от правил; модель без правило-производных признаков, но с графовыми и текстовыми; модель на всех признаках. Параллельно - двойная разметка 100 операций двумя экспертами и расчёт κ. Расхождение результатов разделяет гипотезы: провал всех вариантов -> (1); выигрыш только у графово-текстового -> (2); низкая κ -> (3); расхождение оценок на выборке из очереди и вероятностной -> (4). |
| **Ожидаемый эффект** | Сдвиг Recall@330 относительно сортировки по сумме на классе «транзит» и «обнал»; на «дроблении» ожидание слабое - там правило уже сильное. |
| **Стоимость проверки** | ~300 операций экспертной разметки (≈60 человеко-часов финмониторинга) + 100 операций на двойную разметку (≈20 часов) + 2 недели аналитика. Инфраструктура не требуется - считается на исторических данных. |
| **Критерий остановки** | Если ни один вариант не обгоняет baseline на вероятностной выборке - гипотеза «в данных есть закономерность сверх правил» признаётся неверной: ML-сервис не строится, задача закрывается правилами, бюджет уходит на инициативу №2. Если κ ниже приемлемой - эксперимент останавливается до доработки гайдлайна: мерить нечем. |

## №2 (+№18) - где именно теряется качество извлечения

| Поле | Что фиксируем |
|---|---|
| **Где именно теряем** | На канале «фото с телефона» и на нестандартных бухгалтерских формах - в звене распознавания либо в звене извлечения полей. |
| **Гипотеза причины** | Качество изображения: перекос, блики, обрез - распознавание получает вход хуже того, на котором училось. |
| **Конкурирующие объяснения** | (1) Дело не в качестве снимка, а в незнакомой форме документа (модель не видела таких таблиц). (2) Ошибается не распознавание, а классификатор типа документа - дальше по конвейеру применяется не тот шаблон полей. (3) Распознавание верно, но порог уверенности неоткалиброван: верные поля уходят человеку, неверные принимаются автоматически. |
| **Рычаг** | Данные (добор фото-канала и редких форм), предобработка (выравнивание, устранение бликов), признаки/шаблоны по типам, порог и постобработка. |
| **Дешёвый различающий эксперимент** | Парный набор: 100 документов, снятых одновременно сканером и телефоном. Одинаковая форма, разное качество входа. Падение только на телефонных копиях -> гипотеза о качестве снимка; падение и на сканах -> дело в форме (1). Отдельно - прогон с принудительно заданным верным типом документа: если качество восстанавливается, виноват классификатор (2). Проверка калибровки: доля ошибок среди автопринятых против доли верных среди отправленных человеку (3). |
| **Ожидаемый эффект** | Рост доли автоприёма на фото-канале либо обоснованное решение оставить канал ручным. |
| **Стоимость проверки** | Транскрипция 100 пар документов (≈20 часов операциониста) + неделя аналитика. Сбор парного набора - организационно, на текущем потоке заявок. |
| **Критерий остановки** | Если и на чистых сканах field-accuracy не позволяет верифицировать вместо перенабора - эффекта нет, конвейер не строится. Если падение только на фото - канал остаётся ручным, это не провал проекта, а сужение области применения. |

## №4 - почему прогноз не попадает в факт

| Поле | Что фиксируем |
|---|---|
| **Где именно теряем** | На кризисных когортах и в сегментах с малым числом наблюдений: факт выходит за интервал прогноза. |
| **Гипотеза причины** | Смена макрорежима: историческая зависимость «признаки -> просрочка» перестала держаться. |
| **Конкурирующие объяснения** | (1) Смещение одобренной выборки: модель описывает только одобряемый поток, а состав выдач изменился. (2) Искажённая отчётность заёмщиков (пересечение с инициативой №10) - признаки врут, а не модель. (3) Малый объём событий в сегменте: разброс объясняется случайностью, а не ошибкой модели. (4) Утечка будущего в обучении (макроряд в пересмотренной редакции) - офлайн-оценка была завышена изначально. |
| **Рычаг** | Данные (версионирование макрорядов на дату, reject inference), признаки (модель без признаков отчётности), калибровка и интервалы, стресс-слой поверх модели. |
| **Дешёвый различающий эксперимент** | Бэктест по когортам в трёх вариантах: полная модель; модель без признаков отчётности; модель на данных в редакции «на дату» против пересмотренной. Плюс проверка ширины интервала против размера сегмента. Различает (2) - если без отчётности ошибка падает; (4) - если оценка на данных «на дату» заметно хуже; (3) - если промахи укладываются в разброс малого сегмента. |
| **Ожидаемый эффект** | Возврат покрытия интервала к номинальному либо обоснование, что часть ошибки принципиально не снимается моделью и закрывается стресс-сценарием. |
| **Стоимость проверки** | Данные уже есть, отдельных сборов не нужно: ~2 недели аналитика риск-менеджмента. |
| **Критерий остановки** | Если ни один вариант не обгоняет экстраполяцию винтажей на закрытых когортах - модель не строится, процесс остаётся экспертным, а работа сводится к оформлению интервалов и стресс-сценариев. |
